# 1. Purpose & Vision

Dayflow is a Human Resource Management System (HRMS) built to digitize and streamline core HR operations — employee onboarding, profile management, attendance tracking, leave management, payroll visibility, and approval workflows — for both Admin/HR Officers and Employees.

Beyond replicating a standard HRMS, Dayflow is designed to solve specific operational pain points that traditional HR tools ignore (slow approvals, lack of transparency in payroll changes, unverifiable self-service edits, slow onboarding) and to introduce genuinely novel capabilities — a fairness-first gamification layer and a local, privacy-preserving AI-powered workforce simulator — that differentiate it from a conventional HRMS clone.

The guiding principle across every design decision in this document is: transparency, verifiability, and fairness for the employee, paired with speed and predictive insight for the Admin/HR Officer.

# 2. Scope

The system provides:

* Secure authentication (Sign Up / Sign In) with system-generated Login IDs
* Role-based access control (Admin/HR Officer vs Employee)
* Employee profile management with an admin-verification layer for sensitive edits
* Attendance tracking with daily/weekly views and Check-In/Check-Out
* Leave and time-off management, including a fast-track emergency leave path
* Payroll/salary visibility with a mandatory 30-day advance-notice change workflow
* Approval workflows for HR/Admin across edits, leave, and payroll changes
* A gamification/recognition layer for consistency and reliability
* A What-If Workforce Simulator with a natural-language chatbot interface, powered by a locally hosted small language model (no third-party LLM API calls)

# 3. Definitions & Abbreviations

**Admin / HR Officer:** User with management, verification, and approval privileges across all employee records.

**Employee:** Regular user with limited, self-service access to their own records.

**Time-Off:** Paid leave, sick leave, unpaid leave, or emergency leave.

**Change Request:** A pending, unapplied edit to a record (profile field or payroll component) awaiting verification or a scheduled effective date.

**SLM:** Small Language Model — a locally-run, lightweight language model (via Ollama) used for intent parsing and natural-language generation in the chatbot.

**Provisional Leave:** An emergency/sick leave that is auto-approved on submission and subject to retroactive review.

# 4. User Classes & Characteristics

| **User Type** | **Description** |
| --- | --- |
| Admin / HR Officer | Manages employees, verifies self-service edits, approves leave and attendance exceptions, controls and changes payroll (with notice period), views analytics/reports, runs workforce simulations. |
| Employee | Views and edits (subject to verification) personal profile, tracks attendance, applies for leave (including emergency leave), views own salary details (read-only), participates in gamification/recognition. |

# 5. Core Functional Modules (Baseline HRMS)

## 5.1 Authentication & Authorization

### 5.1.1 Sign Up

* Only Admin/HR can create new user accounts (no open self-registration) — when HR/Admin onboards a new employee, an account is created for them.
* Login ID is auto-generated by the system in the format: CC + First two letters of first & last name + Year of joining + Serial number of joining.
* Example: 0C210C202A0001
* — CC = Value from Company Name
* — First two letters of first & last name = from the employee's name
* — Year of joining = 4-digit year
* — Serial number of joining = sequential number for that year
* A system-generated password is issued on first creation; the user must log in and change it on first use.

### 5.1.2 Sign In

* Users log in with Login ID/Email + Password.
* Incorrect credentials display clear, non-revealing error messages (no hinting at which field was wrong).
* Successful login redirects to the role-specific dashboard.

## 5.2 Dashboard

### 5.2.1 Employee Dashboard (Landing Page)

* Displays quick-access, clickable employee cards (each opens a view-only, non-editable profile page).
* Each card shows the employee's profile picture and basic info, plus a status indicator dot in the top-right corner:
  + Green dot = Present in office
  + Orange dot = On leave
  + Yellow dot = Absent (no time-off applied and not marked present)
* Top navigation bar: Company Logo, Employees, Attendance, Time Off tabs, plus a profile avatar with a status dot.
* Clicking the profile avatar opens a dropdown: My Profile, Log Out.
* “My Profile” opens the employee's own profile in editable form (subject to the verification workflow for sensitive fields).
* A Check In / Check Out systray control lets employees mark attendance; on successful check-in, the status dot changes to green immediately.

### 5.2.2 Admin / HR Dashboard

* Displays the full employee list as clickable cards, attendance records, and pending leave/edit/payroll approvals.
* Ability to switch between employees and view/edit their full profile, including the Salary Info tab (visible only to Admin).

## 5.3 Employee Profile Management

### 5.3.1 View Profile

* Tabs: Personal Info, Private Info, Salary Info (Admin-only), Security.
* Includes: profile picture, About section, Job details, Skills, Certifications, hobbies/interests, date of birth, date of joining, home address, personal email, marital status, phone number, emergency contact.

### 5.3.2 Edit Profile

* Employees can self-edit low-risk fields directly: profile picture, bio/about, hobbies, skills list.
* Employees can request edits to sensitive fields (address, phone number, bank/account details, emergency contact) — these route through the Change Request / verification workflow described in Section 7.2, rather than applying instantly.
* Admin can edit all employee details directly, without the verification step (admin edits are treated as authoritative).

## 5.4 Attendance Management

### 5.4.1 Attendance Tracking

* Daily and weekly attendance views, browsable by date, with Check In/Check Out timestamps, Work Hours, and Extra Hours columns.
* Status types: Present, Absent, Half-day, Leave.
* If an employee's working source is field-based (not office-based), attendance is inferred from assigned tasks rather than Check In/Check Out.

### 5.4.2 Attendance View

* Employees can view only their own day-wise attendance for the current/selected month, including breaks.
* Admin/HR can view attendance of all employees present on the current day, and search/filter historical records.
* Attendance data is the basis for payroll generation: the system uses generated attendance records to determine the total number of payable days per employee. Unpaid leave or missing attendance automatically reduces payable days during payroll computation.

## 5.5 Leave & Time-Off Management

### 5.5.1 Apply for Leave (Employee)

* Employees select: Time-Off Type (Paid Time Off, Sick Leave, Unpaid Leave), date range (validity period), and can attach supporting documents (e.g. sick leave certificate).
* A calendar view shows remaining Paid Time Off and Sick Leave day balances, plus previously applied time-off marked on the calendar.
* Leave request status: Pending, Approved, Rejected.

### 5.5.2 Leave Approval (Admin/HR)

* Admin/HR views all time-off requests in a list view with Reject and Approve buttons per request, filterable/searchable, split by tab (Time Off / Allocation).
* Employees can view only their own time-off records; Admins/HR Officers can view and approve/reject time-off records for all employees.
* Changes reflect immediately in employee records and balances.

## 5.6 Payroll / Salary Management

### 5.6.1 Employee Payroll View

* Payroll data is strictly read-only for employees: Monthly Wage, Yearly Wage, Salary Components (Basic Salary, House Rent Allowance, Standard Allowance, Performance Bonus, Leave Travel Allowance, Fixed Allowance), Provident Fund contribution, Tax Deductions.

### 5.6.2 Admin Payroll Control

* Admin can view payroll of all employees, define Wage Type (Fixed / Percentage of wage), configure salary components, and set # of working days in a week / Base Time (hrs).
* Automatic calculation: each salary component is auto-computed based on the employee's defined wage. Example: if Wage = ₹50,000 and Basic = 60% of wage, then Basic = ₹30,000; if HRA = 50% of Basic, then HRA = ₹15,000.
* Salary component values automatically recalculate when the wage amount changes. The total of all components must not exceed the defined wage — enforced at save time.
* All payroll changes are subject to the 30-day advance notice workflow described in Section 7.1 — admin can no longer silently overwrite live payroll data.

# 6. Identified Problems in the Baseline Design

Through review of the baseline HRMS design, four operational problems were identified that a naive implementation would carry forward:

* Payroll changes made by Admin take effect immediately with no advance notice to the employee, creating confusion and trust issues.
* Employee self-service edits to their own profile apply instantly with no verification step, risking incorrect or fraudulent data entering official records.
* The leave approval process is slow and rigid — especially damaging for sudden/accidental/emergency leave, where employees cannot realistically wait for approval before taking the day off.
* On the technical/organizational side, onboarding and knowledge transfer (KT) for new hires is a slow, unstructured process.

# 7. Problem Solutions — Detailed Design

## 7.1 Payroll Change — 30-Day Advance Notice

Rather than treating a payroll edit as an instant write, every payroll change is modeled as a Change Request with a mandatory future effective date.

* Admin edits a salary/component value → system creates a pending\_change record with effective\_date = today + 30 days (the 30-day window is configurable per organization) and a required reason/comment field.
* The employee is notified immediately upon creation of the change, via the Notification module.
* The employee's Salary Info view displays both the “Current” value and the “Upcoming (effective DD/MM/YYYY)” value side by side, so nothing is hidden.
* Optional employee acknowledgment: the employee can acknowledge they've seen the change (this is a receipt, not an approval — Admin retains final authority).
* Immediate Correction override: for genuine data-entry mistakes, Admin can apply an immediate correction, but this path is logged separately and flagged distinctly from routine changes, so the 30-day guarantee cannot be silently bypassed as a matter of routine.
* A scheduled job (daily) checks for change requests whose effective\_date has arrived and applies them automatically to the live payroll record.

## 7.2 Employee Edit Verification

Employee-submitted edits to sensitive fields do not apply instantly — they create a Change Request containing the old value, the proposed new value, and route to Admin for review.

* Fields are split into two tiers: Self-serve (profile picture, bio, hobbies, skills — apply instantly, low risk) and Verified (address, phone, bank/account details, emergency contact, legal documents — require Admin approval).
* Admin sees a diff view (old value vs proposed value) rather than a full re-entry form, minimizing review effort.
* Admin can Approve (applies the change) or Reject (with a required comment explaining why, visible to the employee).
* Until approved, the employee's official record keeps the old value — downstream processes (payroll, attendance, notifications) are never disrupted by unverified data.
* This uses the exact same underlying Change Request pattern as Section 7.1, implemented once as a shared module and reused by both Payroll and Employee Profile.

## 7.3 Leave Approval — Emergency Leave Fast Track

Standard planned leave keeps the normal Pending → Approved/Rejected workflow. A new Emergency Leave type is introduced specifically for sudden/accidental absences, with different rules designed around real-world urgency:

* Emergency leave is auto-provisionally-approved the moment it is submitted, so the employee's attendance record is correctly marked without them needing to wait on anyone.
* The request is flagged “Provisional” and immediately visible to Admin/HR.
* Admin can retroactively flag or reject a provisional leave within a review window (e.g. 48 hours), which triggers a follow-up conversation with HR rather than blocking the employee upfront.
* Abuse prevention: a configurable cap on how many provisional emergency leaves an employee can use before subsequent emergency requests revert to requiring real-time approval.
* For all other (planned) leave types: an SLA-based escalation — if a request sits Pending beyond a configurable threshold (e.g. 24–48 hours), the system automatically notifies a secondary approver or the requester's reporting manager, so approvals don't stall purely from inattention.

## 7.4 Onboarding & Knowledge Transfer Acceleration

A lightweight onboarding module rounds out the HR story without requiring a full LMS build:

* Role-based onboarding checklist templates — creating a new employee auto-assigns a set of tasks (e.g. “set up laptop”, “read onboarding doc”, “shadow team lead”) with due dates.
* Progress bar visible to both the new hire and Admin/HR, so stalled onboarding is visible early.
* A Buddy/Mentor field on the employee record, assigned by Admin, to give every new hire a named point of contact.
* Each role/department can link to a knowledge-base doc repository (tags/links stored on the role record) rather than building a full wiki from scratch.

# 8. Novel Feature: Gamification & Recognition System

A recognition layer designed to reward genuinely positive workplace behavior without penalizing legitimate rest, sick leave, or time off — an explicit design correction from an early idea of rewarding pure “no leave taken” streaks, which would pressure employees toward unhealthy presenteeism.

## 8.1 What Is Rewarded

* Reliability: consistent on-time check-ins and low unplanned/unapproved absence (measured against unplanned absence, not total leave taken).
* Planning discipline: leave requested with good advance notice (rewards good process, not absence of leave).
* Peer-nominated recognition titles sourced from genuine peer votes — e.g. “Most Helpful”, “Onboarding Buddy of the Month” — decoupled entirely from attendance statistics.
* Reliability streaks explicitly exclude any approved Sick Leave or Emergency Leave from breaking the streak — only unapproved/unplanned absence resets it.

## 8.2 Mechanics

* Badges and trophies are displayed on the employee's dashboard card and profile, visible to everyone in the organization.
* Titles/awards are decided on a monthly and yearly cadence via organization-wide voting.
* Admin-weighted voting: to counter popularity bias, an Admin vote counts for more than a single peer vote (e.g. 1 Admin vote = 3 peer votes), with a configurable cap so no single admin can unilaterally decide an outcome.
* The recognition leaderboard is opt-in per employee, respecting that not everyone wants their attendance/reliability stats made visible to peers.

# 9. Novel Feature: What-If Workforce Simulator & HR Chatbot

The centerpiece differentiator of Dayflow: a simulation interface that lets HR ask hypothetical workforce questions and receive computed, auditable answers — not guesses from a language model.

## 9.1 Example Questions It Answers

* “What happens if 20% of the engineering team takes leave next week?” — computes workforce availability, potential workload redistribution, department capacity, attendance impact, and possible bottlenecks.
* “What if 5 employees resign?” — estimates operational impact on affected departments.
* Open-ended questions grounded in actual office data (attendance history, leave patterns, department headcounts).

## 9.2 Two-Layer Architecture (Critical Design Decision)

The feature is deliberately split into two layers so that the numbers shown to HR are always deterministic and trustworthy, while natural language is only used for the parts of the interaction that benefit from it.

**Layer 1 — Simulation Engine:** Pure, deterministic calculation logic over existing HRMS data (department headcount, active leave records, attendance history). Produces capacity percentages, workload redistribution estimates, and bottleneck flags via structured queries and math. No machine learning involved — this is the layer that must be correct and explainable in a demo.

**Layer 2 — Chatbot / NLP Front-End:** A thin wrapper around a locally hosted small language model (via Ollama) that (a) parses a free-text HR question into structured parameters, e.g. {department: "engineering", percentage: 20, timeframe: "next\_week"}, and (b) turns the Simulation Engine's structured JSON result back into a natural-language answer.

Because the chatbot never invents numbers itself — it only calls the Simulation Engine and rephrases its output — predictions remain fully auditable, which matters for HR tools where a hallucinated headcount number would be a serious trust failure.

## 9.3 Local-Model Constraint

* No calls to third-party LLM APIs (Gemini, OpenAI, etc.) — the model runs entirely on local infrastructure via Ollama.
* A small quantized open-weight model (e.g. Llama 3.2 3B or Phi-3 Mini) is used for both intent parsing and response generation, chosen for response speed on hackathon-scale hardware.
* Intent-parsing calls request structured JSON output directly from Ollama (format: "json"), avoiding fragile regex parsing of free-text model output.

# 10. Non-Functional Requirements

* Security: role-based access control enforced at every module boundary; sensitive fields (payroll, bank details) require elevated permission; JWT-based session auth.
* Transparency: every change to payroll or verified profile fields is logged with old value, new value, requester, approver, and timestamp.
* Auditability: simulation results are always traceable back to the underlying data query, never opaque model output.
* Privacy: no employee data leaves local infrastructure — the chatbot's language model runs on-premises via Ollama.
* Usability: dashboard cards, calendar views, and diff-based approval screens are designed to minimize clicks for the most frequent HR actions (approve/reject, check-in/check-out).
* Extensibility: module boundaries (see Technical Details document) are designed so that individual modules could be extracted into standalone services in the future without a rewrite.
